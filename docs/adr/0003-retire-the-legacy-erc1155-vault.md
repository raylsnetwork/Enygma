# Retire the legacy ERC1155 vault and its VK slots

`Erc1155CoinVault` took receipts only from legacy ERC1155 circuits: `OwnershipErc1155NonFungible`, `OwnershipErc1155Fungible`, `JoinSplitErc1155`, `BatchErc1155`, `JoinSplitErc1155WithAuditor` and `OwnershipErc1155NonFungibleWithAuditor`, in VK slots 2, 3, 4, 5, 15 and 16. None of them has source, a gnark-server route or a keygen entry in the repo, so nobody here can read what they constrain. The vault's checks on them were also weaker than the other vaults' (#417). Its `withdraw` checked no message tag and no opening for zero params, but still spent every non-zero nullifier, so anyone holding someone else's unsettled receipt could burn their notes (R-009). Its spend loop ran over outputs and spent nullifiers whose root was zero (R-065). Withdraw and transfer receipts were not domain-separated (R-064). It took legacy receipts outside tree 0, where the client's two nullifier derivations disagree (R-010). And `deposit` made notes that `withdraw` could not open (R-073).

So the vault is retired, not hardened. `deposit`, `transfer`, `withdraw`, `verifyOwnership` and `checkReceiptConditions` revert `Erc1155VaultRetired`. The vault is no ERC1155 receiver, so a token sent to it directly is refused. Its DvP checks are `AbstractCoinVault`'s, which refuse every leg (see Consequences). It stays deployed as vault 2, so the vault ids keep their numbering. `export_vk_init` always writes an unprovable placeholder VK for the six circuits, whatever key file or earlier JSON exists, because `Erc20CoinVault`'s constants also read slots 2, 3 and 4 (as PaymentFee, PaymentRelayerFee and UsdrFee). In the main deployment, a real legacy VK there would verify a legacy proof as a fee payment.

## Considered Options

- **Harden the legacy paths**: require `WITHDRAW_MESSAGE` and an opening for every non-zero output, spend only nullifiers with a non-zero root, loop over inputs, refuse withdraw receipts in `transfer` and legacy receipts outside tree 0. Rejected: every one of those checks rests on what circuits with no source constrain, which nobody can verify. Deposits would still have no working exit unless `withdraw` learned the deposit's note format, against a circuit that cannot be read either. And no flow, test or deployment uses these circuits.

## Consequences

ERC1155 has no shielded path until a circuit with source replaces these. Notes can still be registered in vault 2 by two paths: the owner-only `EnygmaDvp.privateMint`, once the owner flags vault 2 with `setVaultMintable(2, true)` (no vault starts flagged), and `EnygmaAuction`'s `registerCoins` calls for an auction whose item or bid vault is 2, which first needs a note there to lock. Neither moves tokens, and nothing can spend such a note. Its DvP hooks refuse only through call order: `nullifyFromDvpReceipt` and `insertCommitmentFromDvpReceipt` do not check the leg themselves, and EnygmaDvp calls the vault's `checkDvpReceiptConditions` before either, which refuses every leg with `DvpLegNotSupported`.

The repo records no network deployment: its only network config is the local chain 1337 (`enygmadvp.config.json`). So "which keys each deployment registers" is answered for its deployment scripts. Until #417, `make dvp-stack` (`scripts/stack.sh`, `export_vk_init -placeholder`) and `scripts/init.sh`, the README and `demo/run.sh` (`export_vk_init` without the flag) all registered the real legacy VK in each of the six slots wherever the untracked legacy key files (`gnark_circuits/scripts/keys/*1155*VK.key`) were present, with their proving keys beside them. Where a key file was absent, the slot kept the build dir's earlier JSON. Without one, `-placeholder` wrote a placeholder, and the flagless scripts stopped with an error naming the circuit. Every deployment now registers placeholders in all six slots. Two more ERC1155 slots are outside this decision, because no contract reads them: `JoinSplitErc1155WithBrokerV1` (14) has no key file and always gets a placeholder or a kept JSON, and `BatchErc1155NonFungibleWithAuditor` (17) still exports its real VK where its key file is present. The Payment deployment (`enygmadvp_payment.config.json`) has its own Verifier and only ERC20 vaults, and retail deploys no ERC1155 vault, so neither is affected. Already-deployed vaults are not upgraded: an existing chain keeps the old vault and VKs until it is redeployed.
