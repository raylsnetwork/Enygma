Core
Note Commitment Structure
// Every private note is represented by a Poseidon commitment
Commitment = Poseidon( pk_spend // owner's spend public key
                    || salt // randomness (HKDF-derived or random)
                    || amount // token amount
                    || tokenId // ERC20 token identifier
                   )

Nullifier = Poseidon( sk_spend // proves ownership when spending
                   || leafIndex // position in Merkle tree
                  )
ℹ️
Value Conservation

Without fee: valueIn = Σ valueOut  ·  With fee: valueIn = Σ valueOut + fee
The ZK circuit enforces this — no trusted party can inflate balances.

Optimization
Channel Mode — High-Frequency Payments
⚡
Why Channel Mode?

Standard mode runs a fresh ML-KEM encapsulation per payment (1088-byte capsule on-chain). Channel mode derives a shared key once and reuses it — payments only post a 32-byte channelId instead of a 1088-byte capsule, saving ~90% calldata for the ciphertext field.

Users encrypt their sk_view for the auditor at registration time. The auditor can later recover any user's view key and replay the scanning process — without needing any interaction with the user post-hoc.

Security
AEAD Binding Protection
// At registration: user binds the two ciphertexts together via AEAD AAD
(ss_audit, mlKemAuditCt) ← ML-KEM.Encaps(pk_auditor)
enc_key = HKDF-SHA256(ss_audit, "enygma-audit-view-key-v1")
aesAuditCt = AES-256-GCM.Encrypt(enc_key, dk_view.seed, AAD=mlKemAuditCt)

// If an attacker swaps mlKemAuditCt on-chain with a different capsule,
// the AEAD authentication tag fails when auditor tries to decrypt aesAuditCt
// (because the AAD no longer matches) → protection against ciphertext substitution
Reference
Cryptographic Primitives

Spend Key (Hash-based)

sk_spend ← random field element
pk_spend = Poseidon(sk_spend)
Proves ownership inside the ZK circuit without revealing sk_spend

View Key (ML-KEM-768)

Post-quantum secure key encapsulation.
ek (public, 1184 bytes) stored on-chain
dk (private, kept secret by user / auditor)
Used for non-interactive key agreement per payment

Commitment Scheme

Poseidon hash (ZK-friendly)
C = Poseidon(pk_spend || salt || amount || tokenId)
Stored in a depth-8 Poseidon Merkle tree on-chain

Zero-Knowledge Proof

Groth16 on BN254 curve
Generated by gnark server on port :8082
Verified on-chain by EnygmaDvp (constant gas, ~250k)

Symmetric Encryption

AES-256-GCM (authenticated)
Key derived via HKDF-SHA256 from ML-KEM shared secret
Authentication tag failure = "not my note" signal

Key Derivation (HKDF)

HKDF-SHA256 with domain-separated info strings:
"Bob salt" → payment salt
"Bob symmetric key" → AES key
"enygma-channel-key-v1" → channel key
"enygma-audit-view-key-v1" → audit key

Nullifier

nf = Poseidon(sk_spend || leafIndex)
Prevents double-spending without revealing which note is spent.
Stored in spent set on-chain (EnygmaDvp)

Channel Key

AES-256-GCM with reusable shared key
Derived once via ML-KEM, reused for all payments in a channel
Nonce: random 12 bytes per payment (GCM safety)

🔒
Privacy Properties

Sender privacy: The nullifier hides which note is spent (no link to pk_spend on-chain).
Recipient privacy: Bob's scan is private — he downloads all events so observers can't tell which one he was looking for.
Amount privacy: All amounts are inside commitments and ZK proofs — only the fee (if any) is public.
Auditor access: Controlled via the AEAD-bound audit ciphertexts registered on-chain. Auditor access is non-interactive — users do not need to be online.
