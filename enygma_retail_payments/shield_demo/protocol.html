Observer's ledger

    The view key

    (ekview,dkview)=ML-KEM-768.KeyGen(seedview),seedview∈{0,1}512

    ML-KEM-768 (FIPS 203) is a key-encapsulation mechanism: anyone holding the 1184-byte encapsulation key ek can make a fresh shared secret that only the holder of dk can recover. Its security rests on module-LWE, a lattice problem believed hard for quantum computers as well as classical ones. The wallet draws the 64-byte seed at random; KeyGen is deterministic in it, so the seed is all the wallet keeps of dk. ek_view is published so that anyone can address a note to its owner.

    2The auditor's keys

    The auditor makes an ML-KEM-768 key pair the same way. Users seal their view keys to its encapsulation key when they register, which is what later lets the auditor read their notes.

    (ekA,dkA)=ML-KEM-768.KeyGen(seedA)
    Auditor seedA ekA

    ek_A is public, but it reaches the users' wallets as configuration, not through the chain, so the ledger is still empty.

    Whoever holds dk_A can open every registered user's view key, and so read all of their notes. That is the point of the auditor, and it makes dk_A the one key whose loss undoes everyone's privacy from the auditor's side.

    3Registration

    Each user sends one transaction from their own account: UserRegistry.register(pkSpend, pkView, mlKemAuditCt, aesAuditCt). Before it does, the wallet seals its view key's seed to the auditor.

    What the chain now holds

    Each transaction's calldata is public and permanent, and the ledger now lists it: the keys, the two audit ciphertexts and the account that sent it.

    Sender msg.sender tx block Ana msg.sender tx block
    msg.sender, in amber, links an account to the keys it registered. For a registration that is intended: an entry in the registry is a public identity. On a payment the same link would name the payer, so the full protocol lets a relayer send payments from its own account, for a fee.

    4The shield

    The Sender holds public RaylsERC20 (the issuer minted them to the Sender's account) and deposits all of it into the vault, which turns it into the Sender's first note: one leaf of the vault's Merkle tree. The deposit is one transaction, Erc20CoinVault.depositV2([amount, pkSpend, salt, tokenId], ciphertextI, ciphertextII), sent from the Sender's own account.

    The field every value lives in

    𝔽p={0,1,…,p−1},a+b,a·bmodp,−1≡p−1

    A note's four values, its commitment, every node of the tree, the keys and the nullifiers are all elements of 𝔽p, the scalar field of the BN254 curve: the integers modulo the -bit prime

    p

    The Groth16 proofs of the later steps are made over BN254, so a circuit's wires carry exactly these numbers and its constraints are equations mod p. The arithmetic wraps around: in the field, −1 is p − 1, a valid and enormous amount. That is why the payment's circuit checks that every amount is small (the range check) instead of trusting that none is negative.

    The note commitment, computed by the vault

    C=Poseidon(pkspend,salt,amount,token)

    The vault does not take a commitment from the depositor: it computes C on chain, in depositV2, from the four values in the calldata, after pulling amount tokens from msg.sender. So the note it inserts is bound to the tokens it actually received; a deposit cannot mint a note worth more than it paid. With this run's calldata:

    What a commitment hides, and what this one does not

    A commitment published on its own is hiding: from C nobody learns the amount or the owner. Two properties give that. Poseidon is one-way, so C cannot be run backwards to its inputs. And the salt is random: without it, C would be Poseidon(pk_spend, amount, token), and anyone could hash the owner's public key with amount = 1, 2, 3, … until one matched. With a salt drawn from the field, each guessed amount must come with a guessed salt, one chance in p ≈ 2254. It is also binding: Poseidon is collision-resistant, so no one can find a second opening of C with another amount.

    (ss,c)=ML-KEM-768.Encaps(ekviewowner) salt=HKDF-SHA256(ss,info=“note salt”)modp

    The salt is not drawn and remembered: it is derived from a fresh ML-KEM secret shared with the note's owner, so the owner can derive it again from the chain (Ana's discovery, step 6, opens a note this way). Here the owner is the Sender, and c is ciphertextI.

    This note hides nothing. Its whole opening, pk_spend, salt, amount and token, is calldata, and pk_spend is the key the Sender registered. Anyone can recompute C and see that the Sender's account put into a note the Sender owns. That is the price of entering: the vault has to see the amount it is paid. Privacy starts at the first spend, when the Sender proves they own some leaf of the tree without saying which, and the new notes' openings never touch the chain.

    Poseidon, as a sponge

    absorbs=(0,x1,…,xn)∈𝔽pt,t=n+1 permutes←π(s),π=RF/2full∘RPpartial∘RF/2full rounds squeezePoseidon(x1,…,xn)=s0 rounds←M·S(s+cr),S:x↦x5

    The state is t field elements: one capacity lane, which starts at 0 and is never input, and n rate lanes that take the inputs. Every hash here absorbs its inputs in one block, applies the permutation π once and squeezes one element. A round adds round constants cr, applies the S-box x ↦ x⁵ (to every lane in a full round, to one lane in a partial round) and mixes the lanes with a t × t MDS matrix M. x⁵ is a permutation of the field because gcd(5, p − 1) = 1, which the run checked. The deployed parameters are circomlib's, which target 128-bit security; the rounds themselves are a black box here.

    RF RP,t=2 · pk_spend = Poseidon(sk_spend) RP,t=3 · each node of the Merkle tree RP,t=5 · the note commitment C

    Poseidon is built for this field: its S-box costs three multiplications, so a hash is a few hundred constraints in a circuit, where SHA-256 would cost tens of thousands. One-wayness, collision resistance and the hiding above are assumptions about π, backed by public cryptanalysis rather than a reduction to a classical hard problem.

    The leaf joins the tree

    n0,i=Ci(leafi;an empty slot isz) nk+1,j=Poseidon(nk,2j,nk,2j+1) root=n,0,z=keccak256(“ZkDvp”)modp

    The vault keeps its notes in a binary Merkle tree of depth 8, so 2⁸ = 256 leaf slots. Inserting C rehashes the path from its slot to the root, and the vault records the new root in its history: isValidRoot(tree, root) answers whether a root is one the tree has had. A spend later proves, inside the circuit, that its note is a leaf under such a root, without saying which leaf.

    tree leafi leaves now root z

    The run rebuilt tree with the wallet's Merkle code from every Commitment event the vault had logged, found C at leaf , and checked that its root is the vault's merkleRoot and that isValidRoot holds for it.

    The crowd. Which leaf a spend opens is hidden among the leaves of its tree, so a tree's 256 slots bound the anonymity set. In fact the bound is 255: the vault opens a new tree when a batch of leaves would reach the 256th slot, and a new tree's crowd starts again from one. This tree holds leaves. A spent note stays in the crowd, since its nullifier does not say which leaf it was.

    What the chain now holds

    The ledger adds the deposit: its msg.sender, its calldata in full (the opening, and the note's ciphertexts, which step 6 explains with Ana's note) and the leaf the Commitment event inserted. The mint and the approve before it are public transactions too, with the same account and amount; so are the token's Transfer events.

    msg.sender names the Sender's account as the depositor. For a shield that link is not the leak, since pk_spend in the calldata names the Sender too. It matters on the payment, where the full protocol lets a relayer send the transaction for a fee.
