The math behind key generation

why each primitive was chosen
1SPEND KEY

Poseidon over BN254 — cheap to prove, not cheap to invert

The spend key never leaves the client and is never encrypted for anyone — it only needs one property: a Groth16 circuit must be able to re-derive it from a secret witness at low cost. Poseidon is purpose-built for that: a hash over the same 254-bit scalar field the circuit already computes in, costing a few hundred constraints versus tens of thousands for SHA-256 or Keccak.

seed ← {0,1}²⁵⁶ mod p  ·  sk_spend = Poseidon(seed)  ·  pk_spend = Poseidon(sk_spend)
p is the BN254 scalar field order, ≈2²⁵⁴. Two Poseidon evaluations — not one — separate raw randomness from the provable secret: every later appearance of sk_spend inside a proof (nullifiers, ownership checks) is a fresh Poseidon image, so the witness never repeats itself in a way that would leak the seed. Security reduces to preimage resistance: recovering sk_spend from the public pk_spend costs on the order of searching all ≈2²⁵⁴ field elements.
2VIEW KEY

ML-KEM-768 — built to survive a quantum adversary

The view key exists purely for confidentiality: it lets a sender agree on a fresh shared secret with the recipient non-interactively, then goes untouched until the recipient scans. Elliptic-curve Diffie–Hellman would do this more cheaply today, but it falls to Shor's algorithm on a sufficiently large quantum computer. ML-KEM (FIPS 203) replaces the hard problem underneath with Module-LWE over structured lattices, for which no efficient quantum algorithm is known.

(A, t = A·s + e) ← ML-KEM.KeyGen()  // s, e: small-coefficient secret & error vectors
pk_view = t  (1184 B, public)  ·  sk_view = s  (private)
"768" is the parameter set — NIST security category 3, roughly the classical strength of AES-192. A sender never contacts the recipient to use this key: Encaps(pk_view) samples a fresh (ss, ctxt) pair by masking t with more lattice noise; only the matching sk_view can cancel that noise back out and recover the same ss.
Scoped honestly: this makes key agreement and note confidentiality quantum-resistant, but the payment proof itself is still Groth16 — elliptic-curve pairings, which do fall to a large enough quantum computer. The system today is quantum-private (nobody quantum-capable can read your history), not yet fully quantum-secure (a future quantum adversary could in principle forge a proof) — a distinction worth keeping straight rather than rounding up to "post-quantum" across the board.
3AUDITOR ESCROW

A second, AEAD-bound encapsulation

Registration also lets one designated auditor recover a user's sk_view later — without that user's cooperation — while leaving spending power (sk_spend) completely untouched. This is a second ML-KEM encapsulation, this time against the auditor's public key, chained into an AES-256-GCM encryption of the actual secret.

(ss, mlKemAuditCt) ← Encaps(pk_auditor)
encKey = HKDF-SHA256(ss, info="enygma-audit-view-key-v1")
aesAuditCt = AES-256-GCM(encKey, sk_view, aad = mlKemAuditCt)
Passing mlKemAuditCt as associated data — not as plaintext — binds the two ciphertexts together. Swap one for a different user's and AES-GCM authentication fails outright; escrow material can't be mixed and matched across users even though both sit in the same on-chain table.
4CHANNEL SETUP

A standing ML-KEM handshake, reused for every tagged payment

Unlike the fresh capsule a plain payment encapsulates on every send, a channel is set up once between two people — see the Channel setup card above — and its shared secret is reused for every tag published between them afterwards. Only With Tag mode ever reads this.

(ss, c1) ← ML-KEM.Encaps(pk_view[recipient])
k = HKDF-SHA256(ss, info="enygma-channel-key-v1")
c2 = AES-256-GCM(k, payload, aad = c1)
payload — what actually gets encrypted here{message, senderId} — an optional greeting and an optional sender identifier. Not the payment amount; that never appears in channel setup at all.
Same technique as the auditor escrow above: passing c1 as associated data — not as plaintext — binds c2 to that exact capsule. A c2 from one channel setup can't be paired with a different c1 and still decrypt; AES-GCM authentication rejects the mismatch outright. The resulting ss is what every later tag — Poseidon(blockNumber, pk_spend[recipient], ss mod p) — is derived from, so both sides only ever need to run this handshake the one time.
How it's actually used: (c1, c2) get published to TagChannelRegistry alongside a privacy bitmap. Anyone scanning tries Decaps(sk_view, c1) on every entry; if it's really theirs, they recover ss, derive k, and open c2 to read the message — confirming the channel exists before either side has to do anything else. Wrong candidates just fail AEAD authentication and get skipped, same as everywhere else in the protocol.

How a payment works, in brief

the short version — see the Protocol tab for the full walkthrough

Alice encapsulates a fresh shared secret to Bob's view key (or reuses a channel they've already set up), then derives a salt for Bob's new note and another for her own change purely from that one secret. She builds both output commitments and encrypts the amount for Bob — all locally, before any of it touches the chain.

She then generates a single proof that her input note really exists in the tree, the nullifier is well-formed, and the two output amounts sum correctly back to the input — and submits everything in one transaction. Bob never gets notified: he discovers the payment by trial-decrypting every ciphertext on chain (or, in tag mode, a cheap equality check), recomputes the commitment to confirm it's really his, and can spend it whenever he chooses to scan. Nothing about who paid whom, or how much, is visible on-chain to anyone — except the auditor, who can decrypt what a specific person received using the escrow set up once at registration, never a spend key.

ENYGMA RETAIL PAYMENTS, EXPLAINED

Two keys per person.
One note only they can open.

Enygma Retail Payments lets anyone hold and move ERC-20 value privately on a shared ledger. It rests on the two keypairs each person mints at registration, and on a fresh shared secret every payment derives without ever putting it on chain. Here's how the pieces fit together.

01
KEY GENERATION

Each person generates two keypairs

At registration, every user creates two independent keypairs with very different jobs. Keeping them separate is the whole idea: one keypair authorizes spending, the other lets people find and open payments addressed to you — and never the reverse.

03
KEY AGREEMENT

Sender and recipient derive a shared secret

To pay someone, the sender runs an ML-KEM-768 encapsulation against the recipient's view key. It produces a ciphertext — the "capsule" — and a shared secret. The recipient decapsulates the capsule with their view secret and recovers the exact same secret. Post-quantum key agreement, with no secret ever transmitted — by default, a fresh capsule for every single payment, though two parties who transact repeatedly can set up a channel and skip that, as shown below.

Why bother with a channel?

Two parties who transact often — payroll paying the same employee every cycle, a merchant and a regular customer — don't need a fresh post-quantum key exchange for every transfer. One ML-KEM encapsulation establishes the channel; every payment after that just derives a new salt and key from the same shared secret and skips the capsule entirely. The on-chain payment() call takes the exact same arguments either way — only what cipherText / encTxData mean changes.

04
NOTES, NOT BALANCES

A note is a hash, not a number the chain can add

Retail payments uses a note model, not an account balance: every note is Poseidon(pk_spend, salt, amount, tokenId) — an opaque hash digest, not a homomorphic point. Each payment spends exactly one existing note in full and mints exactly two new ones — a payment note and a change note — whose amounts must sum back to the original.

Why a hash, not a homomorphic point?

Poseidon is a SNARK-friendly hash — cheap to verify inside a Groth16 circuit, a few hundred constraints instead of a full elliptic-curve add gadget. The tradeoff: the chain itself can never check conservation by "adding" two commitments. That arithmetic only ever happens once, inside the proof, on the sender's own device.

The vault checks a proof, not an amount

Every payment carries a proof π shaped to a specific circuit — 1-in/2-out for a plain transfer, 2-in/2-out to merge two notes, or a fee variant. The vault verifies π against the matching VK slot, confirms the nullifier hasn't been used, then applies both new notes atomically — or the whole call reverts.

06
AUDITING

Auditing without custody

An optional auditor holds its own ML-KEM keypair. At registration, a user encrypts their view secret to the auditor's public key — a second encapsulation, AEAD-bound to the first so the two ciphertexts can't be mixed and matched. The auditor can decapsulate that escrow and read the user's incoming traffic on demand. It never receives a spend key, so it can see everything and move nothing.

Two encapsulations, two purposes — but only one has to happen twice

Phase 1's capsule (Bob → auditor) exists purely to protect sk_view; Phase 2's capsule (Alice → Bob) exists purely to protect one payment. Step A only runs once per user — after that, Step B repeats for every payment that user ever receives, reusing the same recovered sk_view. And at no point does any of this touch sk_spend: the auditor can read every amount and never move a single one.

RECIPIENT DISCOVERY

Choosing how visible a channel is

Standing channels (an alternative to a fresh capsule on every payment) publish a bitmap over all registered users — an anonymity set. Only the recipient's bit is ever load-bearing; the rest is cover traffic a chain observer can't tell apart from the real recipient. 08
PRIVATE TAGS

How Bob finds a payment without scanning everything

Plain mode makes Bob work for every note: trial-decapsulate each ML-KEM ciphertext on the vault and see what opens. Once a channel exists between two people (the one-time handshake from step 03, set up ahead of time on Key Setup), the sender can attach a tag instead — a single field element the recipient can check with a plain equality comparison, no decryption attempted until it actually matches. This is the "With Tag" toggle on the Payment tab.

Why not just always use tags?

Tags need a channel first — a handshake both parties complete before a tagged payment between them can exist at all. Plain mode needs nothing set up in advance, at the cost of the recipient's client doing real decryption work per candidate instead of a cheap comparison. Which mode a payment uses is a client-side choice, not something the protocol enforces either way — and how many decoy candidates share a tag window is set by the privacy mode chosen in step 07.

09
SCALE & COST

Constant-time verification, off-chain proving

Privacy is not free: every confidential payment needs a Groth16 proof. Enygma keeps that cost off the chain's critical path — proofs are generated by the sender's own client, and verification on-chain runs in constant time no matter how complex the underlying circuit was.

2VIEW KEY

ML-KEM-768 — the counterparty-addressing channel

The view key exists so a counterparty can agree on a fresh shared secret non-interactively — Alice never contacts Bob to start a swap. Classic Diffie–Hellman would do this more cheaply today but breaks under Shor's algorithm; ML-KEM (FIPS 203) rests on Module-LWE, a lattice problem with no known efficient quantum attack.

3COMMITMENT & NULLIFIER

One note, one leaf, one spend

A private balance is a leaf in a group-specific Merkle tree — fungible assets (ERC-20, most ERC-1155) sit in one vault, non-fungible assets (ERC-721) in another. Spending proves knowledge of the note's secrets and its path to the root, then publishes a nullifier so the same leaf can never be spent twice.

    How registration & issuance work, in brief

    the short version — see the Protocol tab for the full walkthrough

    Registration and issuance are two separate steps because they solve two separate problems. Registering only ever publishes a pair of public keys — a hash-based spend key that authorizes moving a note later, and an ML-KEM view key that lets a counterparty address a swap non-interactively. Neither one, on its own, gives anyone a private balance to actually trade with.

    A balance only exists once an issuer mints one: picking a random salt, hashing it together with the recipient's spend key, amount, and token_id into a commitment, proving that commitment is well-formed with the PrivateMint circuit, and inserting the result as a new leaf in the vault matching the asset's group.     A third, optional key belongs to an auditor: registered on-chain once, it lets an issuer seal an encrypted audit trail to a mint without giving the auditor any ability to spend, block, or see notes that weren't explicitly sealed to them.

    How the whole swap works, in brief

    the short version — see the Protocol tab for the full ten-step walkthrough

    Alice and Bob first agree off-chain on what they're trading — that part never touches the chain. Alice then initiates: she encapsulates a shared secret to Bob's view key, builds three commitments (Bob's payment, her own expected receipt, and a revert only she can spend), and submits a proof (π_A) that the chain checks and admits — locking her nullifier and opening a pending swap, but not yet spending anything.

    Bob then scans the chain, decapsulates, and decrypts the payload meant for him; if the recomputed commitments match, he submits his own proof (π_B) to complete the swap — both nullifiers spend, both new notes land, atomically. If Bob never shows up before the deadline, Alice reclaims her original asset through the revert commitment instead; nothing is ever lost, only delayed. A registered relayer can collapse both legs into one transaction, removing that waiting window entirely.

    How the whole auction works, in brief

    the short version — see the Protocol tab for the full walkthrough

    The seller locks their NFT with a proof of ownership, which mints an auctionId and a pre-committed revert note in case they ever need to cancel.     Answers at the level of the specification: primitives, envelope structure, what leaks and what does not, and where this build deliberately diverges from production.

    30 questions · 6 sections
    Cryptographic primitives
    What cryptography does Enygma actually use?
    Balances
    Pedersen commitments C = v·G + r·H on the proving curve — BN254 in the spec, secp256k1 in this page. Additively homomorphic, perfectly hiding, computationally binding.
    Key agreement
    ML-KEM-768 (NIST FIPS 203, ex-Kyber). Encapsulation runs against a counterparty's registered view key; the chain is both the PKI and the bulletin board for capsules.
    Spend keys
    pk^spend = H(sk^spend) over a 256-bit preimage. Spending is a zero-knowledge preimage proof, never a signature.
    Symmetric
    HKDF-SHA256 expands each pairwise secret into a per-block AES-256-GCM key, a blinding factor and a messaging tag, under separate domain labels. Payloads are AES-256-GCM.
    Proofs
    Groth16 over BN254 — constant-size proof, constant-time on-chain verification.
    ZK hashing
    Poseidon for everything a circuit touches: spend keys, nullifiers, messaging tags, DvP note commitments and Merkle nodes.
    DvP notes
    Hash commitments C = H(pk^spend, salt, amount, tokenId) in a Merkle tree — not Pedersen.
    How is this quantum private?

    Everything protecting confidentiality is post-quantum. Everything protecting integrity is not. The asymmetry is deliberate, and it is the right way round.

    Post-quantum: pairwise secrets come from ML-KEM-768, a lattice KEM with no known quantum attack — so an adversary recording the entire chain today cannot decrypt it after building a quantum computer. Harvest now, decrypt later does not work here. Everything downstream is symmetric or hash-based: r_i, t_i and K^n_ij are HKDF-SHA256 outputs and the payloads are AES-256-GCM. Spend authorization is a hash preimage, where Grover leaves roughly 2128 work against a 256-bit sk^spend. And a Pedersen commitment is perfectly hiding — for uniform r, C is uniform in the group and carries no information about v to any adversary of any power. (Enygma derives r from the pair secret rather than sampling it, so hiding against an outsider rests on HKDF pseudorandomness plus KEM secrecy — both post-quantum, but computational rather than perfect.)

    Not post-quantum: Pedersen binding reduces to discrete log and Groth16 soundness to pairing assumptions on BN254. Shor breaks both. A quantum adversary could open a commitment to a value it never held, or forge a proof — a counterfeit-supply break, not a privacy break. It would learn nothing about anyone's amounts by doing so.

    Closing that gap means replacing the commitment scheme and the proof system with lattice- or hash-based equivalents. That is a contained migration precisely because the key material, the discovery mechanism and the payload encryption are already post-quantum — the parts that leak history if broken later are the parts that are already safe.

    Why does nobody know the discrete log of H?

    If H = d·G with d known, then v·G + r·H = (v + rd)·G and whoever holds d can reopen any commitment to any value — binding collapses and they can mint at will.

    So H is never chosen. It is derived nothing-up-my-sleeve, by hashing a fixed public constant onto the curve: H = Hash-To-Curve(00…00). Anyone can rerun the derivation and confirm it; no party gets a trapdoor, and there is no ceremony to trust. This page derives H the same way, hashing a SHA-512 IV constant to a point on secp256k1.

    Why Poseidon instead of SHA-256?

    Circuit cost is counted in R1CS constraints, and SHA-256 is hostile to arithmetic circuits: its bitwise rotations and XORs have to be bit-decomposed, costing tens of thousands of constraints per compression. Poseidon is defined directly over the proving field with an algebraic S-box, so a permutation costs a couple of hundred constraints instead.

    Every hash on a proven path is therefore Poseidon — pk^spend = H(sk^spend), the nullifier, the messaging tags, DvP note commitments, Merkle nodes. Hashes no circuit sees (HKDF derivation, AEAD) stay on standard SHA-256, where hardware acceleration is the thing that matters.

    This build substitutes SHA-256 for Poseidon everywhere, because WebCrypto ships SHA-256 and not Poseidon. Every structural property demonstrated here — binding, derivation, tag matching, Merkle membership — is unchanged by that swap.

    Why Groth16, and what does its trusted setup require?

    Groth16 has the smallest proofs and the cheapest constant-time verifier of the practical pairing SNARKs. That is the property that matters when a contract verifies a proof on every single transaction: verification cost does not grow with the circuit, so gas per transfer stays flat as the anonymity set and the constraint count grow.

    The cost is a per-circuit trusted setup producing a Common Reference String. If the setup randomness ("toxic waste") survives, its holder can forge proofs — which breaks soundness and therefore supply integrity, but never confidentiality: a forged proof does not open anyone's commitments. Enygma runs the setup as an MPC ceremony among the Privacy Nodes, so soundness survives as long as one participant destroys its contribution. Since every Privacy Node is a regulated institution, that is a defensible assumption.

    Transaction structure
    What exactly does one payment put on chain?

    One fixed-shape envelope, identical no matter how many banks were actually paid:

    Commit₁ … Commit_k ‖ nullifier ‖ t₁ … t_k ‖ π ‖ ctxt₁ … ctxt_k

    k is the anonymity-set size (6 in this build). One commitment, one messaging tag and one ciphertext per slot; one nullifier and one proof per transaction. Because k commitments allow the sender to credit up to k−1 counterparties at once, and each ciphertext can itself carry per-client detail, a single transaction batches at two levels.

    The contract does three things: check the nullifier has not been seen, verify π, and check Σ Commit_i = 𝒪. Then it applies the commitments homomorphically, all or nothing.

    Why is the blinding factor derived rather than sampled at random?

    Because the recipient has to reproduce it. With r_i = Hash(s_ij, n_block), the recipient re-derives r_i from the pairwise secret and the block number, subtracts r_i·H from its commitment and is left with v_i·G. A freshly sampled r_i would have to be transmitted out of band; a derived one makes the commitment self-opening to exactly one party and opaque to everyone else.

    The sender takes the only remaining degree of freedom: r_j = −Σ_{i≠j} r_i. That forces Σ r_i ≡ 0 (mod N), which together with Σ v_i = 0 makes the whole commitment vector sum to the curve identity — the property the contract checks in place of ever seeing an amount.

    Why does the sender's own slot use a different input?

    A sender has no shared secret with itself, so t_j needs some other input — and a careless choice is a fingerprint. Anything public, constant or reused across blocks would let an observer pick the sender's slot out of the k, which is precisely the fact the anonymity set exists to hide.

    Enygma uses t_j = Hash(r_j^prev, n_block): the blinding factor that opens the sender's own previous balance commitment. It is secret, known only to the sender, unpredictable to everyone else, and already a witness in the circuit — so constraining it is free.

    The consequence is visible in the receiving demo: no counterparty's channel secret reproduces t_j, so every recipient's trial ends in "no match" on the sender's slot. That is not a failure — it is the design.

    What does the nullifier prevent, and why is it keyed to the block?

    nullifier = Hash(sk_j^spend, n_block) is deterministic in the spender's secret and the current block, so it is a per-block spend token: one transaction per account per block, enforced by a uniqueness set on chain. Without it, a sender could submit several transactions against the same shielded balance in one block, each individually well-formed, and overdraw.

    Keying it to sk^spend rather than an account index is what makes double-spend prevention compatible with anonymity: the value is a hash of a secret, so it cannot be matched against any registered pk^spend. Keying it to n_block means nullifiers from different blocks cannot be correlated into a spending history for one institution. π constrains it to the same key used in the spend proof, so nobody can fabricate someone else's nullifier to censor them.

    What does the zero-knowledge proof actually prove?

    Six statements, all without revealing which slot the prover occupies:

    • I know the spend secret key behind one of the k public keys in this anonymity set.
    • I know the amount and blinding factor of the commitment holding my balance in this set of k commitments.
    • I am not spending more than I hold.
    • Every unit I debit is credited to other participants in this set — Σ v_i = 0.
    • The nullifier is well-formed: derived from my secret key and the current block number.
    • The messaging tags are well-formed: each derived from the pairwise secret I hold with that participant and the block number, and my own from a blinding factor that opens a commitment in the set.

    What it does not cover: the ciphertexts. Their correctness is deliberately outside the circuit.

    Why is ciphertext correctness left out of the proof?

    Proving an AES-GCM encryption inside a SNARK is expensive enough to put real-time settlement out of reach, and the incentive analysis makes it unnecessary.

    The commitment is well-formed regardless — π guarantees that — so a recipient is credited the money whether or not the payload is honest. A malformed ctxt_i only forces the slower recovery path: strip r_i·H from the commitment and solve for v in v·G. Meanwhile the failure is publicly attributable: the recipient can show that the block key derived from the pairwise secret does not authenticate the ciphertext, and AEAD authentication makes that claim checkable.

    So the attack costs the sender real funds and produces a provable incriminating record against a regulated institution — while keeping the circuit cheap for everyone else. In this trust model that trade is the right one.

    Is a payment to a bank, or to that bank's customers?

    Either, and the protocol does not distinguish them. A commitment credits an account; what that credit represents is carried in the slot's ciphertext, which only the credited bank can open.

    • Interbank settlement. The leg discharges an obligation between the two institutions. The payload is a reference — there are no end customers to name.
    • Client payments. The leg funds specific beneficiaries inside the receiving bank, and the payload enumerates them with their individual amounts. This is the double aggregation the spec describes: one transaction credits up to k−1 banks, and each of those payloads can itself cover many clients.

    Both ride identical envelopes. The commitment is the same object either way, the tag is derived the same way, and the padded ciphertext is the same length — so the chain cannot tell a settlement from a customer batch, and a single transaction can mix the two freely. Only the recipient learns which it received, and only for its own slot.

    Why k ciphertexts instead of one per payee?

    The count is metadata. If only credited slots carried a ciphertext, the envelope would announce how many banks were paid, and their positions would announce which ones. So every slot carries an equal-length ciphertext, and a decoy slot carries a real, openable payload for v = 0.

    Equal length is not automatic — it has to be built. A settlement reference is far shorter than a list of end customers, and a decoy shorter still, so each plaintext is padded to a fixed size before encryption (256 bytes in this build; JSON ignores the trailing padding on the way out). Without that step the ciphertext length would leak both which slots were paid and what kind of payment each leg was.

    Same reasoning for the tags: k tags, all the same width, so a five-way batch and an all-zero dummy transaction are byte-indistinguishable in shape. Fixing k rather than letting the sender pick it closes the same leak at the transaction level.

    Privacy model
    What does a passive observer of the chain learn?

    Learned: the k account indices in the set, k commitments, k equal-length tags, k ciphertexts, one nullifier, one proof — and that the commitments sum to the identity, so value was conserved.

    Not learned: which slot is the sender, which slots were credited, any amount, whether this was a five-way batch or an all-zero dummy, and any balance. Every account starts at Com(0,0) = 𝒪, byte-identical across institutions, so an empty account and a settled one are the same kind of object.

    The residual leak is participation: set membership is public, so an observer knows those k accounts were possibly involved in something.

    How does a recipient find a payment addressed to it?

    For each transaction in the block, the node takes the tag at its own slot and compares it against Hash(s_ij, n_block) for each of the other k−1 members. That is k−1 hashes and no decryption — cheap and fully parallel.

    A match names the sender. From the same pairwise secret the node derives K^n_ij and opens ctxt_i for the transfer detail, and derives r_i to verify the commitment: C_i − r_i·H must equal v_i·G. No match at any candidate means the node is itself the sender of that transaction — or has no channel to whoever sent it.

    Discovery is trivial private information retrieval: each Privacy Node runs a full node, downloads the block and scans locally, so it never reveals to anyone which transactions interest it.

    How is the amount recovered from v·G?

    Normally it isn't. The amount arrives in the ciphertext, and C_i − r_i·H = v_i·G is used as a check on what the sender claimed, not as a recovery step.

    When the payload is missing or maliciously formed, the node is left holding v·G and has to solve a discrete log — tractable only because v is a bounded monetary amount. Three options: a precomputed table of v·G over the plausible range, baby-step giant-step, or brute force up to the deployment's transfer cap. Deployments impose that cap partly to keep this fallback feasible.

    What does v = 0 at my slot mean?

    You were a decoy: in the anonymity set, credited nothing. A transaction in which every slot is zero is a dummy — legitimate cover traffic that adds noise at the cost of one proof.

    A decoy commitment is Com(0, r_i) with a freshly derived r_i, so on chain it is a uniformly distributed curve point exactly like a paying one. Only the holder of that slot can tell the difference, and only after trialing the tag.

    What happens if two banks never ran key agreement?

    There is no s_ij, so the sender cannot derive that slot's r_i or t_i and cannot place that bank in the anonymity set at all — not even as a decoy. On the receiving side, that bank has no candidate secret to trial against the sender's tag.

    Coverage of the shared-secret matrix is therefore a hard operational constraint on both the achievable anonymity set and the discovery mechanism, not bookkeeping. Three pairs are deliberately left unagreed in this build, which is why some trial rows read no channel — cannot derive.

    What does the anonymity set hide, and what does it not?

    Within a single transaction it hides which of the k slots sent and which were credited; an observer's best guess at the sender is 1/k.

    It does not hide that those k accounts appeared together. Over many blocks an observer accumulates a participation graph, and intersection analysis across transactions — not any single envelope — is the relevant threat. The defenses are set composition, dummy traffic, and the fact that per-block nullifiers and per-block tags cannot be linked across blocks, so co-occurrence is the only signal available.

    Auditing & governance
    How does a regulator get visibility without custody?

    At registration a bank encapsulates against the auditor's ML-KEM key, encrypts its own sk^view under the resulting secret, and publishes ("audit", B, ctxt_audit, ctxt_B) on chain. The auditor decapsulates with its view secret and recovers sk_B^view.

    From then on the auditor can re-derive every pairwise secret that bank holds, and so can run the same tag trial, open the same payloads, re-derive the same blinding factors and independently recompute each channel commitment to check it against the matrix.

    It never receives sk^spend. Since spend authority is proven only by knowledge of that preimage, the auditor can see everything and move nothing. Visibility and control are separate keys — that is the entire reason for the two-keypair split.

    What are the disclosure granularities?
    One block
    Disclose the ephemeral key K^n_ij for a single block, encapsulated to the auditor and accompanied by a ZK proof that it was correctly derived from the pairwise secret — so the auditor can trust the key without ever holding the view key.
    One channel
    Disclose the pairwise secret, opening every transaction between that pair of counterparties and nothing else.
    Full history
    Delegate sk^view. Complete visibility of that bank's activity, still zero spend authority.

    Per-block key rotation is what makes the narrowest tier meaningful: because K^n_ij = HKDF(s_ij, n_block), handing over one block's key says nothing about the same channel's earlier or later traffic.

    What can the operator do — and what can it never do?

    The operator holds the contract owner key. It can halt transfer, withdraw and deposit — a circuit breaker that makes those calls revert — and it governs issuance parameters.

    It cannot read: it holds no view key and no pairwise secret, and freezing the contract grants no visibility whatsoever. It cannot spend: balances move only against a valid π over a spend key it does not hold. Freezing is a liveness power, never a confidentiality or authorization one.

    How is supply integrity checked if no balance is visible?

    By adding points. Because commitments are additively homomorphic, summing every account's balance commitment yields a commitment to the aggregate: Σ C_i = Com(Σ v_i, Σ r_i). Issuance is on the public record, so anyone can verify that this summed point equals the commitment to the issued supply.

    A transfer cannot change it: the envelope's own commitments sum to 𝒪, so adding them to the ledger leaves the aggregate fixed. The contract's check path performs exactly this comparison. At no point is any individual balance revealed — the invariant is verified entirely on aggregate curve points.

    Delivery versus payment
    Why does DvP use hash commitments rather than Pedersen?

    The two protocols optimize for different things. Payments needs additive commitments: the contract updates balances by adding points and verifies conservation by summing them, which only a homomorphic scheme permits.

    DvP needs atomic exchange of specific assets. A note has to bind an owner, an asset id, an amount and a salt into a single leaf, be provable as a member of a Merkle tree, and be consumable exactly once. C = H(pk^spend, salt, amount, tokenId) does all of that in one Poseidon hash and hides all four fields behind a preimage. Homomorphism would buy nothing here, and an account-balance model cannot express "this exact bond against that exact cash."

    What does bridging from Payments into DvP actually do?

    It converts one commitment type into the other in a single call. Enygma.withdraw takes a vector of commitment deltas together with DvP deposit parameters, so the same transaction debits a Pedersen balance and mints notes.

    The bank posts Com(−amount, −r) against its own account and Com(+amount, +r) against the DvP escrow account. The pair sums to 𝒪, so the supply invariant is untouched — value is not leaving the system, it is changing representation. The escrow commitment is the Pedersen mirror of the notes now in the tree, and the new leaf C = H(pk^spend, salt, amount, tokenId) is inserted at the next index.

    Modelling note: on chain withdraw does not adjust totalSupply — only minting does — so this build carries the escrow account explicitly. That keeps Σ balances = issued supply visibly true across the bridge instead of appearing to leak value.

    What makes a swap atomic?

    Alice's leg posts, in one transaction, everything both outcomes will need: C^out_B (Bob's side of the trade), C^out_A (what Alice receives), C^rev_A (Alice's refund note), nf_A, a deadline, π_A, and the payload addressed to Bob. swap_id = H(C^out_A, C^rev_A, nf_A, C^out_B, deadline) binds them into one object, and nf_A is marked locked rather than spent.

    From there exactly two terminal states exist. Bob completes before the deadline: π_B is verified, nf_A and nf_B both become spent, and both output leaves are inserted. Or the deadline passes and anyone can revert: the locked nf_A is consumed and C^rev_A is inserted, returning Alice's asset. There is no reachable state in which one leg settles alone.

    How does Bob discover and validate his side of a swap?

    Alice encapsulates against Bob's ML-KEM view key and derives, from that one shared secret under distinct HKDF labels, salt_B^out, salt_A^out and the payload encryption key. Bob decapsulates, derives the identical values, and authenticates the payload with AEAD.

    Then he does the check that matters: he recomputes C^out_B himself from pk_B^spend, the derived salt, and the amount and token he was told, and compares it to the commitment sitting on chain. If they match, the swap posted publicly is provably for the terms he was quoted — established without any circuit proving that Alice encrypted honestly.

    If any check fails, Bob simply does nothing. The deadline reverts the swap and he has lost nothing but time.

    Can anyone tell which notes have been spent?

    No — and the tree is structurally incapable of recording it. A spend publishes nf = H(sk^spend, leafIndex) and proves in zero knowledge that some leaf in the tree opens under the key behind that nullifier, with the Merkle path and the leaf index kept private. The statement is, in effect: here is a nullifier for a leaf in the tree, I know its spend key and a path to it, and my output amounts sum to that leaf's amount.

    So the contract cannot evaluate "is that note spent?". It can only evaluate "have I seen this nullifier before?", in that order: if the nullifier is already in the set the transaction reverts immediately, and only otherwise is the proof verified and the nullifier added. That is the entire double-spend defence, and it works without linking a nullifier to a leaf.

    The tree is therefore append-only and carries no spent flag. Only a leaf's own holder can decide whether it is still spendable, by recomputing its nullifier and testing membership in the published set. This is why the notes table on the DvP tab has no status column: any such column would be information nobody actually has.

    What does the chain learn about a swap?

    Leaf hashes, nullifiers, a Merkle root, a swap id and a deadline. Because pk^spend is inside the note hash, a leaf hides its owner as well as its asset and its amount — the tree is not a table of who holds what, it is a set of opaque digests. Nullifiers are H(sk^spend, leafIndex), unlinkable both to any registered key and to any leaf, so the tree never records which leaves are still live.

    What is public is timing and lifecycle: that a swap of something was proposed against something, and that it later settled or reverted. Amounts, assets and both counterparties stay hidden.
